# 材料池

出题用的材料来源。这里的每一篇是一份**事实骨架**——从公开发表的报道里逐条抽出的事实
（一条一个事实，带数字、带限定语），不是原文，也不含原文的句子。

## 为什么在这里

材料要随应用发到用户手上，所以它跟代码走同一套流程：改动看得见（审材料就是看 diff）、
有历史、能回滚、发布与审计用的是同一份。抓取与提炼用的临时件、被判不合格的淘汰件都是
过程产物，不进这个目录。

## 一篇骨架长什么样

```
# 标题
来源：<原始地址>
发布：YYYY-MM-DD
主题：<主题一>、<主题二>

## 背景
## 做法（已经发生的）
## 成效
## 争议 / 难点
## 建议 / 主张（还没发生的）
```

五栏是按**这件事发生了没有**切的：`做法` 只装某个主体为了解决问题已经采取的措施，
`建议 / 主张` 装谁提了但还没做的。分不清就会被出题反过来利用——题干问「提出改进建议」时，
材料里躺着整段现成建议，等于把答案写在题面上。

规矩全在 `docs/材料规范.md`，这里不重复。

## 怎么更新

```bash
npm run materials -- fetch rmw 10        # 人民网各频道，按栏目拿最新
npm run materials -- fetch rmrb 10       # 人民日报电子版
npm run materials -- fetch gov 养老服务 3  # 政策文件库，按关键词搜
```

抓下来的东西**不合格不落盘**：入库判断不过的直接丢，淘汰件留在 `LIANTAI_MAT_DIR`。
改动当前的提炼规矩之后，用 `redo` 把池子里已有的文章重提炼一遍：

```bash
npm run materials -- redo all
```

池子变大了要发出去，见 `docs/发布与更新.md` 的「材料发布」一节。

## 审什么

发布前跑一次抽检，脚本会把条目拿回原文逐条比：

```bash
npm run materials -- verify 24
```

它只报不改——判错是人的事，脚本不该悄悄擦掉。输出里 `说过头` 与 `错` 两类要逐条看：
抽样错率长期在 8% 上下，错的全是同一族——**限定语被抹掉**（主体、语气、时间、范围）。
这个噪声底是 prompt 这一层压不动的，剩下的靠发布前这一道人工看。
