# 发布与更新（细节）

`AGENTS.md` 的「依赖与更新」节只留边界与硬规矩；**流程细节、验包规矩、卡点都在这一份**。要发版、要动更新链、要换机器时先读它。

## 发布流程

```bash
npm run release          # Windows 侧：盖章 → 出包（--publish never，组件源内置 npmmirror 兜底）→ 建 Release → 逐个 gh 上传并对账
npm run release:mac      # macOS 侧：盖章 → 出包 → 给 zip 签出 .sig → 把 mac 六件补到同一个 Release → 按实际资产逐个对账
npm run release:check    # 只读对账：资产齐不齐、两个 yml 的 version 是不是这一版、有没有占住 latest 却没带 latest.yml、远端安装包字节与本地产物是否一致（sha256）、官网数据跟没跟到本版；另带本仓库自检（package.json 三铁律 + 文档引用的仓内路径都存在）
npm run site:data        # 两边都发完之后：把官网要显示的版本号与更新日志写进 site/，提交推送即上线（Pages 自动部署）
```

## mac 包的发布侧签名（一次性初始化）

```bash
node tools/mac-key.mjs --init      # 只做一次：生成密钥对，私钥写 ~/.liantai-release-key（0600）
# 把打印出来的公钥钉进 update.js 的 MAC_UPDATE_KEYS，提交推送
node tools/mac-key.mjs --pubkey    # 核对一下当前私钥对应的公钥（指纹对不上就别发）
```

- 为什么要有：mac 链的 sha256 期望值与下载地址都是**同一份 Release 元数据**里的值，元数据被改（账号被盗、有人拿 token 发了一版）时两个值一起改，那道校验必然通过。签名只有本机私钥做得出，验不过就拒收（宁可先不更新）。
- 每版都要签：`release:mac` 自动对每个 zip 签名并上传 `.sig`，**没私钥就停手**（没签名的包传上去等于发了一版别人装不上的东西——已装版本会在「检查」这步拒收）。
- 私钥丢了：已装版本只认钉进去的那把公钥，会拒绝一切更新，**手动下一次安装包就恢复**。要在不手动重装的前提下换钥，先把新公钥加进 `MAC_UPDATE_KEYS` 数组发一版（数组允许多把），再用新私钥签下一版。
- 换机器发版：把 `~/.liantai-release-key` 拷过去（或 `--key` 指到它），否则 `release:mac` 会直接停下并告诉你缺什么。

- **发布前必须先提 `package.json` 的 `version`**（版本号不变，老用户永远收不到这一版）。**同一个版本号发第二次**是否被挡，看 Release 里 `latest.yml` 在不在：在，说明 Windows 这半已经传过，该提版本号；不在，说明是 mac 先发的（`release:mac -- --create --prerelease` 建的），脚本不拦，直接把这半补进去。想整版重出先 `gh release delete vX.Y.Z --yes --cleanup-tag`。`package-lock.json` 里那两处版本号由发布闸门盯着，两处不同版就发不了（跑一次 `npm install` 补齐再提交）。
- `release:mac` 的开关：`--dry-run` 不联网只看会传什么；`--skip-build` 不重新出包（复用本机已装的那份产物）；`--create` 才自己建 Release，**单发 mac 必须再加 `--prerelease`**。
- `release:check` 不接参数就查 `package.json` 当前版本，也可以 `npm run release:check -- v0.0.14` 查指定版。
- **发布闸门**（`tools/gate.mjs`）：`npm run release` 与 `release:mac` 开头自动跑四条——工作区干净、远端 `main` 的 sha = 本地 HEAD、跟踪文件里没有明文密钥（`sk-` 各家形态 + GitHub 令牌；演示/测试用的假 Key 在那一行加 `gate-allow` 标记放行）、`package-lock.json` 的版本号 = `package.json` 的版本号（`npm install` 会把 lock 改成当前版本，两处不同版就会脏了工作区）。任一不过就停手，`--skip-gates` 跳过；`node tools/gate.mjs` 可单跑。`release:check` 是发完之后的对账：**「读不到 yml 内容」「GitHub 没回 digest」算失败**（不再静默跳过），字节对账跳过几项也会打印出来。
- **发布必须对账**：electron-builder 给每个 target 各跑一次发布流程，第二个会撞 `tag_name already_exists` 中断——`latest.yml` 与 `.blockmap` 常就在这一步丢，而少了 `latest.yml` 自动更新压根不会启动。所以 `release.mjs` 不信返回码，出完包按产物逐个对账、缺的用 `gh` 补传；`latest.yml` 永远覆盖上传（它是指针，留着旧的会被当成「已有」跳过）；`npm run release -- --reconcile-only` 只对账不出包。打包失败则直接停手不建 Release（空 Release 会占住 `/releases/latest` 让存量 Windows 用户检查更新 404）；两个发布脚本建 Release 都带 `--target <本地 HEAD>`，tag 不会指到远端别的提交上。
- 对账前会校验 `dist/latest.yml` 的 `version` 与 `sha512` 是否就是当前产物：**别拿上一次试打包残留的清单去对账**，否则会把旧版本号或错哈希写到线上（客户端表现为「版本号是新版、内容是旧版」或「下完校验失败」），两种都不会在打包阶段报错。
- **本地产物名与线上资产名是两套**：本地是中文 `练习台-Setup-X.Y.Z.exe`（`build.nsis.artifactName`），传上去改叫 ASCII 的 `liantai-desktop-setup-X.Y.Z.exe`（`release.mjs` 建一个别名链接再传，`latest.yml` 里写的是 ASCII 名）——`dist/` 里找不到 ASCII 名不是打包失败。
- mac 侧六个资产：`latest-mac.yml` + dmg 与 zip 各一份 + 各自 `.blockmap` + **zip 的 `.sig`（发布侧签名）**。`npm run release:mac` **必须带上 `.zip`**（换包下的是 zip，不是 dmg）。没 `.sig` 的版本，已装版本会在「检查更新」那一步直接拒收。
- 发布后删掉 `dist/` 里旧版本的安装包、blockmap 与 `win-unpacked` 残留，只留最新一版三件套（供断网对账）；mac 这边 `dist/mac-arm64/` 是验收目录，验完删，留的是 dmg / zip / 各自 blockmap / zip 的 `.sig` / `latest-mac.yml`。
- gh 在这台 mac 上装在 `~/.local/opt/gh/bin/gh`（脚本自己会找：PATH 里没有就退回这里），发之前要登一次（存在钥匙串里）。仓库公开，没登录时会退回匿名 API，`release:check` 照样能跑。

## 验包（不许碰本机那份安装）

NSIS 安装器按 AppId 找「上一版」，安装前会先静默卸载它——`/D=<临时目录>` 只改文件装到哪，挡不住这一步。0.0.13 发布时按旧规程装到临时目录验证，结果把本机那份 0.0.12 连目录带卸载项一起卸了，桌面与开始菜单快捷方式也被改指到临时目录（用户数据在 `%APPDATA%\liantai-desktop`，不受影响）。三条规矩：

- **验「打包产物能不能起」**：跑 `dist/win-unpacked/练习台.exe`——同一份产物，不装、不写注册表、不动快捷方式。要真正零接触还得补两样：用 `--user-data-dir=%TEMP%\liantai-verify` 起（不碰真实 `%APPDATA%\liantai-desktop`），并加 `LIANTAI_UPDATE_FEED=http://127.0.0.1:<本地源端口>/` 指本地源。它和用户手上那份共用单实例锁与 18743 端口，所以**他正在用的时候不要起**，跑完删临时目录。
- **验「安装器本身」**：只在沙箱里做（另开一个 Windows 用户或虚拟机）。**没沙箱就不验**——代价就是本机在用那份被卸掉。
- **万一真在本机跑了**：先把当前版本的安装包从 Release 留一份，跑完用 `/S` 静默装回去，再核三处归位：`%LOCALAPPDATA%\Programs\liantai-desktop` 目录、`HKCU\...\Uninstall` 里的卸载项、桌面与开始菜单快捷方式指向。

**验 mac 包不用沙箱**：dmg 不是 NSIS 那种会先卸上一版的安装器，`dist/mac-arm64/练习台.app` 可以直接起（配 `--user-data-dir=<临时目录>` 就不碰真实记录）。**未签名 ≠ 打不开**：本机出的包没有 quarantine 标记，双击就能跑；但从浏览器 / 微信下下来再打开会被 Gatekeeper 拦，右键「打开」放行，或 `xattr -dr com.apple.quarantine "/Applications/练习台.app"`。

## mac 版与 Windows 版的不同

- `build/icon.icns` 由 `tools/make-mac-icon.py` 从 `build/liantai-app-icon-v3.png` 生成：macOS 图标是 1024 画布 + 图形 824 居中（四周透明 100px），直接把 Windows 那张满幅方图当 icns 用，Dock 里会比其他图标大一圈。
- `main.js` 的 `applyMenu()` 在 darwin 上必须留 `editMenu`——mac 的 Cmd+C/V/A/Z 是菜单 role 提供的，菜单一清空，作答框里连复制粘贴都不响应（这工具就是靠打字练的）。
- darwin 不走 electron-updater，走 `initMacUpdater` 那条自实现换包链（未签名，Squirrel.Mac 要求更新包与本体签名一致，硬走只在用户机器上报签名校验失败）。这条链的完整性有两道：sha256（与下载地址同源）+ **发布侧签名**（私钥只在本机，见开头那节）。
- **换包全程在同一个卷上改名**：脚本先把临时目录建在目标目录里（`dirname $TARGET`），新包先落 `.liantai-new.<pid>.app`、旧包先改名 `.liantai-old.<pid>.app`，两次 `mv` 都在同一卷 = rename（原子、瞬间）；跨卷时 `mv` 会退化成「复制 200MB 再删」，那段时间正式位置上会出现半个应用。包身份也核两道：JS 侧看当前 `.app` 的 `CFBundleIdentifier`，脚本侧再看新包里的同一字段（光比版本号的话，一个版本号写一样的别的应用能披换上去）。
- **换包脚本里变量后紧跟中文必须写 `${VAR}`**：macOS 自带 bash 3.2 会把中文标点并进变量名，`set -u` 下坏包分支会在写日志与重开旧版之前退出。
- `tests/shell.mjs` 的 `loadUpdate` 把平台钉成 `win32`，mac 那条分支在第 1b 组单独量——不钉的话，同一份自检在 mac 上会整片失败（而状态机本身没错）。第 6 组（假源 + 临时目录把换包脚本真跑一遍）只在 macOS 上执行，别的平台打印一行「跳过第 6 组」（没有 `ditto` / `PlistBuddy`，不是漏测）。

## 更新链在代码里的位置

- 状态机在 `update.js`（壳侧），页面侧接在 `__updatePush()`。
- 壳暴露 `GET /__update/status`；动作用 POST：`/__update/check`（两平台都走）、`/__update/download`、`/__update/install`（后两个只有 mac 链用）。**每个 POST 都要 `x-liantai: 1` 头**——跨站发 POST 会先 OPTIONS 预检，这道头能挡住。
- **备用源**：元数据与安装包拆在两条源上——官方元数据（`OFFICIAL_FEED`，generic 指向 `releases/latest/download/`，单段 Range）配第一条镜像的包，元数据源连不上就按 `BACKUP_FEEDS` 顺序换，换后包地址由 `installCrossSourceHook` 改写指向它的下一条——**相邻两条同时活着才算一条能走通的路**。下载阶段某一条不通时按 镜像 → 镜像 → 官方直连 依次推进（`advanceDownloadSource()`），全试完才落 error。设了 `LIANTAI_UPDATE_FEED` 就只认它（不拆也不兜底）。
- **差量缓存自检**：`installer.exe`（NSIS 写）与 `current.blockmap`（electron-updater 写）可能指向两个版本，`alignDifferentialCache()` 在每次检查前核对——blockmap 里 `sizes` 逐块相加应等于安装包大小，对不上就删 `current.blockmap`（退成全量，不会出错）。
- mac 那条链的入口是 `initMacUpdater` + 安装脚本 `MAC_INSTALL_SCRIPT`；自查只推「有新版本」，下载与换包各要用户点一次（`status.autoDownload === false`）。换包只允许从 `github.com` / `*.githubusercontent.com` 取（明文 http 只放本机回环）；失败写 `<userData>/updates/install.log`，下次启动由 `macLastFailure()` 读出来；下载好没换成的包由 `macScanDownloaded()` 认回来；坏包改名 `.zip.bad`。
- 免安装版（带 `PORTABLE_EXECUTABLE_FILE`）自动更新置 `disabled`。

## 测试副本（npm run test:build）

`tools/build-test.mjs` 打一只与正式版并存、数据分家的 app：

- 包内埋一个标记文件（`tools/build-test.mjs` 临时写入、打完就撤），壳认到它就换 userData 到 `…-test`、把端口固定成 18744（`localStorage` 按 origin 分区，撞上就是又一套空存储）、**不接更新链**（否则自动更新把自己顶成正式版，被测的东西当场消失）。
- bundle id 与显示名带 test（Finder 里两个 app 不打架），不写发布源；产物落 `dist-test/`，与 `dist/` 分开。
- 正式版端口 18743。

## 更新链的已知卡点

- **组件源**：electron-builder 要下的 electron / winCodeSign / nsis 默认从 github.com 拉，本机到那里时通时断（实测 `connect ETIMEDOUT 20.205.243.166:443`，卡在 packaging 之后那一步就是缺 winCodeSign）。`tools/release.mjs` 与 `打包.bat` 都设了 npmmirror 兜底（外部已设则不覆盖）。
- **偶发假死**：electron-builder 偶发在 `downloaded label=electron progress=100%` 之后长时间不动（extraction 已完成但零写入，实测停 13 分钟）。确认卡死后结束进程、删掉 `dist/win-unpacked.tmp` 与 `.tmp.lock` 再重跑，通常 2–3 分钟就过。打包中途失败不会破坏 `dist/` 里上一版的安装包（builder 写的是新目录，最后才替换）。
- **差量省不了多少，别当卖点**：2026-09-24 实测 0.0.12→0.0.13，全量 84.6MB、待下 56.5MB（2756 个变化块），只省约三分之一；那一次差量包组装后校验没过，又退成了整包下载（前后约 141MB）。差量失败只会退全量，不会出错，日志里是 `Cannot download differentially, fallback to full download: Error: sha512 checksum mismatch…`。
- **差量的两个前提**：缓存 `%LOCALAPPDATA%\liantai-desktop-updater\installer.exe`（上一版安装包）在，且**源上旧版的 `.blockmap` 别删**。generic 源支持 `multipart/byteranges` 才是真差量（不支持就优雅退化）；GitHub 资产 CDN 对多段 Range 返回 501，但 `BaseGitHubProvider` 写死单段逐段请求（206 可用）。
- **网络现实**：国内直连 GitHub 时 `checkForUpdates` 可能直接 `ERR_CONNECTION_TIMED_OUT`（真机见过）。这不是 bug：失败会按规则重试且不阻断使用；要稳定就换源（`LIANTAI_UPDATE_FEED`）。
- **Windows 侧拉取**：直连 git 协议不通，用转发站一次性 fetch——`git fetch "https://gh-proxy.com/https://github.com/lllvernan-blip/liantai-desktop.git" main && git merge --ff-only FETCH_HEAD`。**别改 origin，更别用它推送**（它带令牌）。历史被改写那台要 `git reset --hard FETCH_HEAD` 重新对齐。
- **推送凭据**：这台 mac 已跑过 `gh auth setup-git`——gh 就是 git 的凭据助手（全局配置里是 `!/Users/nan/.local/opt/gh/bin/gh auth git-credential`，用绝对路径、不依赖 PATH），所以 `git push` 直连可用。`tools/push-via-api.mjs` 退成备用（留给「github.com:443 被掉、但 api.github.com 还通」的机器，比如旧的 Windows 机器）：**用它推完不会更新本地的 `origin/main` 跟踪引用**，`git status` 会谎报「ahead N」——对账前先 `git fetch origin main`。

## 官网（`site/`）

一页下载页，单文件、零依赖，与安装包同一个仓库（`site/` 不在 `build.files` 白名单里，进不了包）。
线上地址 `https://lllvernan-blip.github.io/liantai-desktop/`，由 `.github/workflows/pages.yml` 部署：
`site/` 有改动推到 `main` 就重新部署一次，也可以手动点一次。

**发完版还有一步，不做官网就指着旧版**：

```bash
npm run site:data     # 写 site/latest.json 与 site/changelog.json，然后提交推送
```

- `site/latest.json`：两个平台各自的版本 / 发布日 / 包名 / 字节数，从线上 Release 读出来生成。
  **prerelease 也算**（这个仓库拿它表示「只发了一个平台」），两个平台各取自己最新有产物的那一版 ——
  所以 mac 单发一版时，Windows 那栏还指着上一次的正式包，不会给用户一个不存在的下载链接。
- `site/changelog.json`：从 `app/index.html` 的 `CHANGELOG` 抽一份（单一真源，站点不另写一份）。
- **忘了跑的后果**：页面一级读不到这两个文件，就只剩页面里写死的那个版本号可用——网站上会一直显示上一版
  （2026-10-17 撞过：页面指着 0.0.21，点下载拿的是旧包）。`npm run release:check` 盯着这一步：
  本版就是最新那版、站点却没跟到它，会直接报出来。

页面自己的几条硬规矩：

- **下载先走加速线路**（与应用内更新同一批源里挑一条）：本机实测直连 github.com 只有 ~29 KB/s，
  100 MB 的包要下很久。**域名不在页面上写出来**——用户面前只有一个下载按钮，不需要知道中间过了哪一站；
  这条线路整个抽掉时的退路是「点了没反应？」那个折叠（先等一会，不行就去官方发布页自己挑）。
- **按钮按这台电脑的平台给包**（认 UA，认不出当 Windows，另一个平台挂在「不是这台电脑？」那行），
  一屏仍然只有一个主行动。
- **取数两级**：`latest.json` → GitHub API（自己筛，**不能用 `/releases/latest`**：它只认非 prerelease，
  会给用户一个落后好几版的号）→ 页面里写死的数。
- 页面自检在 `tests/site.mjs`（按平台给包、加速线路、页面上不写线路域名、mac 单发时不指不存在的包、
  两级都拿不到时的兜底），跑在 `node tests/run.mjs` 里。

## 材料发布（materials/）

材料池**不随安装包走**：它的时效线是半年，有自己的更新节奏，每刷新一次就发一版太重。
池子本体在仓库的 `materials/pool/`（进 git = 改动看得见、有历史、能回滚，**审材料就是看 diff**），
发布到 GitHub 上一个固定 tag 的 prerelease（tag `materials`，**prerelease 不占 `/releases/latest`**，
不干扰 Windows 侧 electron-updater 那条链）：

```bash
npm run materials -- fetch rmw 10     # 抓 + 提炼（真调用，一篇一次）
npm run materials -- verify 24        # 抽检：条目回原文逐条对，只报不改
npm run materials:pack                # 打包 + 签名 + 自检 + 发布
```

`tools/materials-pack.mjs` 做的四步：

1. 把 `materials/pool/` 打成一个 JSON（`liantai-materials.json`，含打包时的提交 sha）；
2. 用**发布侧同一把私钥**（`~/.liantai-release-key`）签名，签名格式与 mac 包共用 `macSigPayload`；
3. **自检**：拿钉在 `update.js` 里的公钥验这份签名。验不过就停手——签了但应用不认，等于发了一份
   用户永远收不到的东西。这一步不是拿本机私钥自己验自己（那只能证明签名没打错）；
4. `materials/` **有未提交的改动就拒绝发布**：池子的审计面就是 git diff，工作区脏了这次发布
   就没有可审的对应物。

应用侧在 `update.js` 的「材料同步」：启动后 20 秒拉一次，成功过就 12 小时内不再拉，失败一小时后退避重试。
拉下来先验签再落盘，落盘是「写临时名 → 改名就位」（rename 原子，读到的一篇不会是半截），
写完把包里没有的旧篇删掉（池子整个由包管，一份被判不合格的材料下架后本机不能还留着）。
**任何一步失败都是没声的**：池子照旧用本机已有的（或随包的兜底），界面回落编材料，不报错、不弹窗。

安装包里仍带一份兜底（`build.files` 的 `materials/**/*`）。**只在池子还是空的时候播**——
已经有池子的（上一版播过或同步下来过）一律不覆盖，否则一个旧兜底会把新同步的盖回去。

验收用一个回环假源（`LIANTAI_MATERIALS_API`，与 `LIANTAI_RELEASE_API` 同一个思路）：真签名、真下载、真验签，
不必拿 GitHub 跑——`tests/shell.mjs` 的「材料同步」一组共 16 条断言，包括「换一把私钥签 → 整包拒收」
「下载途中改一个字节 → 拒收」「包里没有签名文件 → 不收」「本机一把公钥都没有 → 拒收」。
